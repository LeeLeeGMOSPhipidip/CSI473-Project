# Rremmogo Consistency Matrix

## Conventions 
The matrix is based on the current proposal, requirements, acceptance criteria, business rules, CRC cards, domain model, quality scenarios, and use-case model.

## Matrix
| Use-case step | Proposed sequence message | CRC/domain responsibility | State or lifecycle effect | Requirement / rule / acceptance evidence |
|---|---|---|---|---|
| **Sign in - 1.** Student enters account credentials. | `signIn(ubEmail, password)` | `Account` authenticates the Student and protects account access. CRC currently assigns this to `User`. | Account must be active; no Rental state change. | FR-02; Business rule: only valid UB users may use the system. |
| **Search for items - 1.** Customer enters an item name or category. | `searchItems(query, category)` | `ItemListing` provides searchable details; `Category` supports classification/filtering. CRC currently assigns this to `Customer`, `Item`, and `Category`. | No state change. | FR-05, FR-06; Quality Scenario 2. |
| **View available items - 1.** System returns only matching available listings. | `findAvailableListings(criteria)` | `ItemListing` protects its availability and quantity. | Guard: `[availableQuantity > 0 AND status = AVAILABLE]`. | FR-07, FR-11; Business rule: quantity must be greater than zero. |
| **View item details - 1.** Customer selects a listing and views its details. | `getItemDetails(listingId)` | `ItemListing` supplies name, category, condition, description, rental price and available quantity. | No state change. | FR-04; Successful Rental Request acceptance criterion. |
| **Send rental request - 1.** Customer enters the rental period and submits the request. | `sendRentalRequest(listingId, rentalPeriod, quantity)` | `Rental` validates the request with `Account` and `ItemListing`. CRC `RentalTransaction` currently owns rental creation and duplicate-rental protection. | Guard: `[signed in AND valid UB account AND quantity available]`. | Successful Rental Request acceptance criterion; proposal workflow. **Requirement gap: no functional requirement currently states that a Customer may submit a rental request.** |
| **Send rental request - 2.** System creates the rental record. | `createRental(customer, owner, listing, period, quantity)` | `Rental` records parties, listing, period, quantity and status. | `Rental: initial -> REQUESTED`. | Successful Rental Request acceptance criterion; Quality Scenario 3. |
| **Send rental request - 3.** System notifies the Owner. | `notifyOwner(rentalId)` | `Rental` coordinates the notification. | Rental remains `REQUESTED`. | Successful Rental Request acceptance criterion. |
| **Send rental request - A1.** Requested quantity is unavailable. | `rejectUnavailableRequest()` | `ItemListing` prevents quantity from dropping below zero; `Rental` prevents duplicate rental. | No Rental is created; existing Rental and ItemListing states remain unchanged. | Prevent Duplicate Booking acceptance criterion; FR-07; business rule on availability. |
| **View rental request - 1.** Owner views the request. | `viewRentalRequest(rentalId)` | `Rental` supplies Customer, listing, rental period and status. | Rental remains `REQUESTED`. | Use-case model; proposal workflow. |
| **View rental request - 2.** Owner accepts the request. | `acceptRentalRequest(rentalId)` | `Rental` records acceptance; `ItemListing` reserves the requested quantity to prevent double-booking. | `Rental: REQUESTED -> ACCEPTED`. Requested quantity becomes reserved and is excluded from storefront availability. | Proposal Objective 2; revised availability rule needed for the identified inconsistency. |
| **View rental request - A1.** Owner rejects or cancels the request. | `cancelRental(reason)`; `releaseQuantity(quantity)` | `Rental` records cancellation; `ItemListing` releases reserved quantity. | `Rental: REQUESTED/ACCEPTED -> CANCELLED`. | Proposal Objective 2 and Objective 3. |
| **Chat with user or admin - 1.** Customer and Owner agree on arrangements. | `sendMessage(rentalId, content)` | `Conversation` contains `Message`; only participants may communicate. CRC currently uses `ChatMessage`. | No Rental state change. | FR-12; CRC ChatMessage protection; Quality Scenario 4. |
| **Payment confirmation - 1.** Customer confirms making payment outside the system. | `confirmPayment(rentalId)` | `PaymentConfirmation` records the confirming Student and time; `Rental` prevents duplicate confirmation. | Rental remains `ACCEPTED` until both parties confirm. | FR-08; proposal workflow and explicit out-of-scope payment constraint; business rule requiring both confirmations. |
| **Payment confirmation - 2.** Owner confirms receiving payment. | `confirmPayment(rentalId)` | Second `PaymentConfirmation` is recorded; `Rental` checks that Customer and Owner have both confirmed. | Guard: `[customerConfirmed AND ownerConfirmed]`; payment-confirmation condition becomes satisfied, but Rental remains `ACCEPTED` until handover. | FR-08; Payment Confirmation acceptance criterion, corrected to two-party confirmation. |
| **Payment confirmation - A1.** Both confirmations are not present after 48 hours. | `checkPaymentConfirmationDeadline()`; `notifyParticipants()` | `Rental` checks confirmations and coordinates notifications. | Rental remains `ACCEPTED`; it must not become `ACTIVE`. | Handling Payment Not Confirmed acceptance criterion. |
| **Confirm item handover - 1.** Relevant parties confirm collection/handover. | `confirmHandover(rentalId)` | `Rental` verifies payment confirmation, records the due date and activates the rental; `ItemListing` updates quantity. | Guard: `[both parties confirmed payment]`; `Rental: ACCEPTED -> ACTIVE`. | Proposal core workflow. **Requirement gap: handover/collection confirmation is not stated in requirements.md.** |
| **Overdue check - A1.** Due date passes without confirmed return. | `checkDueDate()`; `markOverdue()`; `notifyParticipants()` | `Rental` enforces due date, flags overdue and coordinates notifications. | `Rental: ACTIVE -> OVERDUE`. | Return and Overdue Management acceptance criterion; proposal exception; Quality Scenario 6. |
| **Confirm item return - 1.** Customer records return confirmation and condition. | `confirmReturn(rentalId, condition)` | `ReturnConfirmation` records the Student, time and condition; `Rental` prevents duplicate confirmation. | Rental remains `ACTIVE` or `OVERDUE` until both parties confirm. | FR-09; proposal core workflow. |
| **Confirm item return - 2.** Owner confirms receiving the item. | `confirmReturn(rentalId, condition)` | Second `ReturnConfirmation` is recorded; `Rental` checks both confirmations and closes the transaction. | Guard: `[customerConfirmed AND ownerConfirmed]`; `Rental: ACTIVE/OVERDUE -> COMPLETED`. | FR-09; business rule on completed rentals. |
| **Confirm item return - 3.** System restores the returned quantity. | `increaseAvailableQuantity(quantity)` | `ItemListing` updates availability without exceeding total quantity. | Listing becomes visible whenever `availableQuantity > 0`. | FR-07, FR-11. |
| **Rate user - 1.** Either participant rates the other. | `submitRating(rentalId, score, comment)` | `Rating` stores feedback and links it to the Rental and participating Students. | Guard: `[Rental = COMPLETED]`; Rental state unchanged. | FR-10; business rule: only completed rentals may be rated. |
| **Manage disputes - 1.** Student reports a late, damaged, cancelled or disputed rental. | `submitReport(rentalId, type, description)` | `Report` records the issue; `Administrator` reviews and resolves it. CRC Administrator owns dispute resolution. | `Report: OPEN -> UNDER_REVIEW -> RESOLVED/DISMISSED`; Rental state may remain unchanged. | FR-13; proposal Objective 3; business rule on administrative reports.
